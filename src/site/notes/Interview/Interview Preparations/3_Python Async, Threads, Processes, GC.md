# Управление памятью

Управление памятью в CPython гибридное: подсчет ссылок (Reference Counting), который отвечает за немедленное уничтожение объектов, и циклический сборщик мусора на основе поколений (Generational Garbage Collector), который периодически находит и разрывает изолированные циклические связи между контейнерами.

### Подсчет ссылок (Reference Counting)

Каждый объект (`PyObject`) содержит в своем заголовке поле `ob_refcnt`.

- **Увеличение `ob_refcnt`:** происходит при создании ссылки, присваивании новой переменной, передаче в функцию или сохранении в структуру данных (список, словарь).
    
- **Уменьшение `ob_refcnt`:** происходит при выходе из области видимости, вызове `del`, очистке контейнера или переприсваивании переменной.
    
- **Удаление:** когда `ob_refcnt` падает до 0, мгновенно вызывается C-функция для освобождения памяти.

### Циклический сборщик мусора (Generational GC)

Подсчет ссылок фатально сбоит на циклических структурах. Если объект `A` ссылается на `B`, а `B` ссылается на `A`, их `ob_refcnt` никогда не станет равен 0, даже если внешние переменные `a` и `b` удалены.

```python
# Пример циклической ссылки
a = []
b = []
a.append(b)
b.append(a)
del a, b  # ob_refcnt обеих структур остался равен 1
```

Для решения этой проблемы модуль `gc` отслеживает только **составные объекты (контейнеры)** — объекты, способные хранить ссылки на другие объекты (списки, словари, таплы, пользовательские классы, функции). Простые типы (`int`, `str`, `bytes`) в циклический GC не попадают.

#### Поколения (Generations)

GC делит отслеживаемые объекты на 3 поколения, основываясь на гипотезе о том, что большинство объектов умирают молодыми:

- **Generation 0:** Новые контейнеры. Проверяется чаще всего.
    
- **Generation 1:** Объекты, пережившие хотя бы одну сборку в Gen 0.
    
- **Generation 2:** Долгоживущие объекты (пережили сборку в Gen 1).

#### Алгоритм поиска циклов (Cycle Detection)

1. GC выбирает поколение для сборки (и включает в нее все более младшие поколения).
    
2. GC проходит по всем объектам. Если объект A ссылается на объект B, GC вычитает 1 из счётчика ссылок(`gc_refs`) объекта B. Задача этого этапа — математически "отключить" все ссылки, которые объекты внутри группы держат друг на друга.
    
3. После вычитания проверяются итоговые значения `gc_refs`:

	- `gc_refs > 0`: На объект есть живая ссылка _снаружи_ цикла (например, активный запрос FastAPI или глобальный кэш Redis). Объект помечается как "живой". Он также спасает от удаления все объекты, на которые ссылается.
    
	- `gc_refs == 0`: Все ссылки на объект исходили исключительно от других участников этой же группы. Внешнего доступа к ним нет. Весь этот цикл признается мусором и удаляется.

#### Когда вызывается GC

- **Автоматически по порогам (Thresholds):** Вызов происходит, когда разница между количеством созданных и удаленных контейнеров превышает установленный лимит для Gen 0. (По умолчанию для Gen 0 порог равен 700)
    
- **Явно:** Через прямой вызов `gc.collect()`. В высоконагруженных системах иногда отключают автоматический GC (`gc.disable()`), из-за того что в памяти может находиться большое количество объектов, проверять которые можно только вне обработки важных запросов.
    
- **При завершении интерпретатора:** Осуществляется финальный проход по остаточным объектам.

### Новости и последние обновления

- **Immortal Objects:** Ключевые объекты (`None`, `True`, `False`, маленькие числа, встроенные типы) теперь помечаются как "бессмертные". Их `ob_refcnt` игнорирует инкремент и декремент. Операции очистки и перезаписи ячеек памяти оказались дороже, чем просто хранить их.
    
- **Смена структуры Gen 0:** В CPython 3.12 список объектов поколения 0 разбит на две части ("young" и "incremental"), чтобы GC не проверял объекты, которые создаются во время его работы.
    
- **Stop-The-World GC:** В сборке без GIL (`--disable-gil` / `--without-gil`), так как единого GIL больше нет, циклический GC в free-threaded сборке на короткое время останавливает работу всех execution-потоков для корректного обхода графа объектов.

### Задачи

#### Задача 1. Иллюзия удаления через `del`

Посмотрите на код и ответьте: когда именно объект `Node` будет удален из памяти?

```python
import gc
import weakref

class Node:
    pass

gc.disable()

a = Node()
b = Node()
a.child = b
b.parent = a

ref = weakref.ref(a)

del a
del b

print(ref() is None)
gc.collect()
print(ref() is None)
```

**Ответ:**

- Первый `print` выведет `False`. Команда `del a` лишь удаляет имя `a` из локальной области видимости. Из-за циклической связи `a.child` и `b.parent` у обеих структур `ob_refcnt == 1`.
    
- Второй `print` выведет `True`. После принудительного вызова `gc.collect()` алгоритм определит замкнутый цикл, обнулит ссылки и вызовет деструктор, после чего слабая ссылка `ref()` станет `None`.
    

#### Задача 2. Влияние аргументов на `sys.getrefcount`

Что выведет данный код?

```python
import sys

data = [1, 2, 3]
print(sys.getrefcount(data))

def process(val):
    print(sys.getrefcount(val))

process(data)
```

**Ответ:**

- Первый `print`: `2`. Первая ссылка — имя `data` в модуле. Вторая — временная ссылка, возникшая из-за передачи объекта в качестве параметра внутри самой функции `sys.getrefcount()`.
    
- Второй `print`: `4`. Ссылки формируются следующим образом:
    
    1. Глобальная переменная `data`.
    2. Аргумент `val` внутри стекового кадра функции `process`.
    3. Временная ссылка в стеке аргументов интерпретатора при вызове `process(data)`.
    4. Временный аргумент внутри вызова `sys.getrefcount(val)`.

#### Задача 3. Воскрешение объекта (Object Resurrection)

Что произойдет при выполнении этого кода?

```python
import gc

resurrected = []

class DeadMan:
    def __del__(self):
        print("Finalizing...")
        resurrected.append(self)

obj = DeadMan()
obj_id = id(obj)

del obj
gc.collect()

print(len(resurrected))
print(id(resurrected[0]) == obj_id)
```

**Ответ:** Код выведет `Finalizing...`, затем `1` и `True`. Внутри `__del__` ссылка на уничтожаемый объект (`self`) сохраняется в глобальный список `resurrected`. `ob_refcnt` объекта снова возрастает с 0 до 1. Сборщик мусора обнаруживает "воскрешение" объекта и отменяет освобождение памяти.


# Threads и GIL

### Зачем нужен GIL

Главная причина наличия GIL — простота и производительность однопоточного кода при управлении памятью.

CPython использует подсчет ссылок (`ob_refcnt`). Если бы несколько потоков параллельно меняли счетчики ссылок одних и тех же объектов, возникли бы гонки состояний в памяти CPython. Чтобы защитить `ob_refcnt` без GIL, потребовалось бы:

- Сделать оператор изменения счетчика ссылок атомарным (высокий оверхед на уровень CPU-инструкций).
    
- Использовать мелкозернистые мутексы для каждого объекта или пула памяти, что неизбежно приводит к взаимным блокировкам (deadlocks) и гигантскому падению скорости однопоточного кода.

### Что такое Thread

Потоки в CPython (`threading.Thread`) — это реальные потоки операционной системы (1:1 mapping с pthreads в Linux/macOS и Win32 Threads в Windows).

### Как работает GIL в связке с ОС

GIL – это по факту некоторый флаг в памяти и набор C-инструкций по его смене/проверке.
ОС по своему усмотрению выдаёт потокам процессорное время (возможность исполнять код). Но так как выполнение кода Python — это пошаговое исполнение инструкций байткода внутри C-цикла интерпретатора, то этот самый C, на каждом шаге проверяет состояние GIL.
Пример:
- **ОС дает процессор Потоку 1.** Поток 1 просыпается на физическом ядре CPU.
    
- **Поток 1 пытается выполнить Python-код.** Для этого его C-код смотрит на мьютекс GIL.
    
- **Если GIL занят Потоком 2:** Поток 1 понимает, что работать нельзя. На C-уровне он вызывает функцию ожидания мьютекса (`pthread_mutex_lock`) и **засыпает**. Он отдаёт процессор обратно ОС, даже не израсходовав выделенное ему время!
    
- **Поток 2 работает свои 5 миллисекунд.** Таймер CPython срабатывает, Поток 2 сам отпускает GIL.
    
- **ОС будит Поток 1.** Поток 1 наконец захватывает GIL и начинает крутить байткод Python.

### Новости и последние обновления

- **Python 3.12 (Per-Interpreter GIL):** Появилась возможность создавать несколько независимых интерпретаторов внутри одного процесса Python. У каждого из них свой GIL, поэтому они могут работать на разных ядрах CPU параллельно.
    
- **Python 3.13 (Free-Threaded CPython / PEP 703):** Введена официальная сборка Python **без GIL** (`--disable-gil`). GIL полностью удален, а счетчики ссылок и память защищаются новыми, более точечными механизмами на уровне CPU. Теперь потоки могут выполнять Python-код честно параллельно на всех ядрах.

### Задачи
#### Задача 1. Конкурентная модификация общего состояния (Data Race)

Что выведется в консоль и почему? Что надо исправить?

```python
import threading

account_balance = 0

def deposit():
    global account_balance
    for _ in range(100_000):
        account_balance += 1

threads = [threading.Thread(target=deposit) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()

print(f"Final balance: {account_balance}")
```

**Ответ:**
Код выведет случайное значение меньше `200000` (например, `142310`).
Причина заключается в том, что GIL защищает только внутренние структуры CPython, но не обеспечивает атомарность операций на уровне Python-кода. Операция `account_balance += 1` раскладывается на несколько инструкций байткода, между которыми планировщик CPython может переключить GIL.

```python
# Правильное решение: использование явной блокировки
import threading

account_balance = 0
balance_lock = threading.Lock()

def deposit():
    global account_balance
    for _ in range(100_000):
        with balance_lock:
            account_balance += 1
```

#### Задача 2. Взаимная блокировка (Deadlock) при использовании нескольких Lock

Объяснить, почему данный код зависает, и предложить решения.

```python
import threading
import time

lock_a = threading.Lock()
lock_b = threading.Lock()

def transfer_a_to_b():
    with lock_a:
        time.sleep(0.01)  # Имитация I/O
        with lock_b:
            print("Transfer A -> B complete")

def transfer_b_to_a():
    with lock_b:
        time.sleep(0.01)
        with lock_a:
            print("Transfer B -> A complete")

t1 = threading.Thread(target=transfer_a_to_b)
t2 = threading.Thread(target=transfer_b_to_a)
t1.start(); t2.start()
t1.join(); t2.join()
```

**Ответ:**
В коде происходит классический Deadlock (перекрестный захват ресурсов):
1. Поток `t1` захватывает `lock_a` и засыпает на `time.sleep()`, освобождая GIL, но сохраняя владение `lock_a`.
2. Поток `t2` захватывает GIL, берет `lock_b` и засыпает на `time.sleep()`.
3. Поток `t1` просыпается, запрашивает `lock_b` и засыпает, так как `lock_b` занят `t2`.
4. Поток `t2` просыпается, запрашивает `lock_a` и засыпает, так как `lock_a` занят `t1`.

Оба потока ОС заблокированы навсегда в ожидании мьютексов друг друга.

```python
# Решение 1: Соблюдение строгого порядка захвата ресурсов
def transfer_b_to_a_fixed():
    with lock_a:  # Всегда первым захватываем lock_a
        time.sleep(0.01)
        with lock_b:
            print("Transfer B -> A complete")

# Решение 2: Использование таймаута при захвате
def transfer_b_to_a_timeout():
    acquired_a = lock_a.acquire(timeout=1.0)
    if acquired_a:
        try:
            # Выполнение логики
            pass
        finally:
            lock_a.release()
```


# Процессы

## Способы создания

```python
import multiprocessing as mp

# Задается до создания процессов
mp.set_start_method('spawn')
```

### 1. `fork`

Вызывает системный вызов `fork()`. Дочерний процесс получает точную копию адресного пространства родителя через механизм Copy-on-Write (CoW).
- **Как используется:** По умолчанию использовался в Unix-системах (до Python 3.14).
- **Когда применяется:** В простых однопоточных скриптах CLI или при запуске веб-серверов (например, мастер-процесс Gunicorn создаёт воркеры через `fork`), где передача состояния родителя дочерним процессам нужна "из коробки" без затрат на сериализацию.
- **Плюсы:** Мгновенный старт, память не копируется физически до первой записи.
- **Минусы:** Небезопасен в многопоточных программах. Скопированные мутексы родителя могут навсегда остаться в заблокированном состоянии в дочернем процессе.

### 2. `spawn`

Запускает полностью новый процесс интерпретатора CPython. Родительский процесс не копируется; дочерний процесс исполняет только необходимый модуль и функции.
- **Как используется:** По умолчанию на Windows и macOS, а начиная с Python 3.14 — на всех платформах.
- **Когда применяется:** В многопоточных приложениях, сервисах с асинхронными циклами (asyncio), при интеграции с C-библиотеками (OpenCV, PyTorch) или при вызове процессов из GUI.
- **Плюсы:** Абсолютная безопасность памяти и отсутствие перенесенных блокировок.
- **Минусы:** Медленный запуск (требуется поднятие интерпретатора с нуля) и обязательная сериализация всех аргументов через `pickle`.

### 3. `forkserver`

Создает единый чистый серверный процесс. Все последующие дочерние процессы запрашиваются у этого сервера через `fork()`.
- **Как используется:** Задается вручную (`mp.set_start_method('forkserver')`).
- **Когда применяется:** В высоконагруженных системах с фоновыми потоками, где требуется частый и быстрый спавн короткоживущих процессов, но классический `fork` небезопасен.
- **Плюсы:** Быстрее, чем `spawn`, и безопаснее, чем `fork`, так как серверный процесс гарантированно однопоточный.

## Межпроцессное взаимодействие (IPC)

Так как память процессов изолирована, передача данных требует специальных механизмов Inter-Process Communication.

### 1. Сериализация (Queue / Pipe / Manager)

Данные преобразуются в байты с помощью `pickle`, передаются через сокеты или сокет-пары (pipes) ОС, и десериализуются в дочернем процессе.

- **Ограничение:** Высокий оверхед по CPU и памяти при работе с большими объектами. 

### 2. Разделяемая память (Shared Memory)

Использует системные вызовы. Память выделяется в виде общего блока, доступного обоим процессам напрямую.

- **Применение:** Передача массивов данных (например, NumPy arrays) без копирования и сериализации через `multiprocessing.shared_memory.SharedMemory`

## Проблемы и узкие места

- **Deadlocks при сериализации:** Передача огромных объектов через `multiprocessing.Queue` может заблокировать процесс, если внутренний OS pipe переполнится до того, как дочерний процесс успеет вычитать данные.
    
- **Orphan Processes:** Если родительский процесс завершается аварийно (SIGKILL), дочерние процессы продолжают исполняться в системе как "зомби" или сироты.

## Особенности pickle и альтернативы

Модуль `pickle` — это встроенный механизм бинарной сериализации графа объектов Python в поток байтов и обратно.

### Особенности `pickle`

- **Сериализует почти всё:** Поддерживает пользовательские классы, рекурсивные структуры данных, лямбды (с ограничениями), исключения.
    
- **Тесная связь с CPython:** Сохраняет ссылки на классы по их полному импортируемому имени (`__module__`, `__qualname__`).
    
- **Небезопасен:** Распаковка невостребуемых байтов (`pickle.loads()`) позволяет исполнить произвольный код через метод `__reduce__`.

### Альтернативы сериализации

| **Формат / Метод**                         | **Принцип работы**                                                   | **Отличия от pickle**                                                                                                                                     |
| ------------------------------------------ | -------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`dill` / `cloudpickle`**                 | Расширенная версия `pickle`.                                         | Умеет сериализовать лямбда-функции, замыкания, генераторы и методы классов в runtime. Медленнее, но гибче.                                                |
| **JSON / Protocol Buffers**                | Структурированные форматы данных.                                    | Работают значительно быстрее, но требуют строгой схемы или не поддерживают специфичные объекты Python (байтовую память, экземпляры произвольных классов). |
| **Zero-Copy Protocols (PyArrow / Plasma)** | Передача через Shared Memory в едином бинарном формате Apache Arrow. | Не сериализуют объекты в байты для отправки по сокету. Дочерний процесс читает структуры данных прямо из оперативной памяти без фазы десериализации.      |

# Asyncio

`asyncio` реализует кооперативную многозадачность в рамках **одного потока** ОС. В отличие от ОС, которая принудительно вытесняет потоки, в `asyncio` корутины добровольно отдают управление обратно планировщику с помощью ключевого слова `await`.

Вместо того чтобы блокировать весь поток при ожидании сетевого ответа или чтения файла, корутина доходит до ключевого слова `await` и добровольно возвращает управление Event Loop. При этом она оставляет "закладку" (Future) и сообщает, какого именно события ждет. 

Event Loop берет из своей очереди следующую готовую задачу и начинает выполнять её. Когда операционная система сообщает, что данные для первой корутины готовы, Event Loop "будит" её, и выполнение продолжается с места остановки. Это позволяет одному потоку обрабатывать десятки тысяч I/O-операций конкурентно, не простаивая в ожидании.

| **Концепт**              | **Описание**                                                                                                                                                                       |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Coroutine (Корутина)** | Функция, объявленная через `async def`. Сама по себе при вызове не выполняется, а лишь возвращает объект корутины. Исполняется только при передаче в Event Loop или через `await`. |
| **Future (Фьючерс)**     | Низкоуровневый объект-обещание. Инкапсулирует результат асинхронной операции, который еще не готов, но появится в будущем (или ошибку).                                            |
| **Task (Задача)**        | Обертка над корутиной (наследуется от Future), которая автоматически планирует ее выполнение в Event Loop.                                                                         |

## Синхронизация и управление задачами (Примитивы)

### Event

Флаг состояния (True/False). Одна корутина устанавливает флаг, остальные ждут его появления. Нет памяти срабатываний: если флаг установлен до вызова `wait()`, ожидание просто пропускается.

```python
import asyncio

cache_ready = asyncio.Event()

async def worker(worker_id: int):
    # Воркеры ждут, пока кэш не будет загружен в память, прежде чем брать задачи из очереди
    await cache_ready.wait()
    print(f"Воркер {worker_id} начал обработку данных с актуальным кэшем")

async def cache_warmer():
    print("Начало прогрева кэша из БД...")
    await asyncio.sleep(2)  # Имитация долгого I/O запроса
    print("Кэш загружен")
    # set() мгновенно разблокирует и запустит всех ожидающих воркеров одновременно
    cache_ready.set()
```

### Condition

Улучшенный Event. Позволяет корутине захватить блокировку, проверить условие и уснуть до изменения состояния, после чего разбудить одну (`notify()`) или все ожидающие задачи (`notify_all()`).

```python
import asyncio

cond = asyncio.Condition()
batch = []

async def event_receiver(item: dict):
    async with cond:
        batch.append(item)
        # Сигнализируем фоновому воркеру
        cond.notify()

async def batch_inserter():
    async with cond:
        while True:
            # Спим и не блокируем Event Loop, пока в массиве не наберется 100 записей.
            # wait_for инкапсулирует цикл while, защищая от ложных пробуждений.
            await cond.wait_for(lambda: len(batch) >= 100)
            print(f"Выполняем массовый INSERT {len(batch)} записей в PostgreSQL")
            batch.clear()
```

### Semaphore

Ограничивает количество корутин, имеющих одновременный доступ к ресурсу. Незаменим при парсинге или обращениях к БД для защиты от исчерпания пула соединений.

```python
import asyncio
import aiohttp

# Жесткий лимит: не более 15 одновременных TCP-соединений к стороннему API, 
# чтобы избежать блокировки по rate limit (HTTP 429 Too Many Requests)
api_semaphore = asyncio.Semaphore(15)

async def fetch_user_data(session: aiohttp.ClientSession, user_id: int):
    # Если 15 корутин уже находятся внутри этого блока, 16-я уснет здесь и будет ждать
    async with api_semaphore:
        async with session.get(f"https://api.example.com/users/{user_id}") as resp:
            return await resp.json()
```

### Barrier

Заставляет группу из N корутин заблокироваться на определенной точке. Все продолжат работу только когда последняя корутина достигнет барьера.

```python
import asyncio

# Ждем инициализации ровно 3 критических подсистем перед тем, как поднять HTTP-сервер
startup_barrier = asyncio.Barrier(3)

async def init_postgres():
    await asyncio.sleep(1)  # Имитация коннекта
    print("PostgreSQL готов")
    await startup_barrier.wait()

async def init_redis():
    await asyncio.sleep(0.5) 
    print("Redis готов")
    await startup_barrier.wait()

async def init_kafka():
    await asyncio.sleep(2)  
    print("Kafka готова")
    await startup_barrier.wait()
    
    # Этот код (и аналогичный в других корутинах после wait) выполнится 
    # только тогда, когда самая медленная задача (Kafka) достигнет барьера
    print("Инициализация успешно пройдена, открываем порты.")
```

### Shield

Оборачивает корутину, защищая ее от внешней отмены (`cancel`). Если родительская задача отменяется, `shield` поглотит исключение, а внутренняя корутина продолжит работу.

```python
import asyncio

async def charge_credit_card(user_id: int, amount: float):
    # Критически важная операция со сторонним платежным шлюзом.
    # Если прервать ее на середине, деньги могут списаться, но статус в нашей БД не обновится.
    await asyncio.sleep(2) 
    print(f"Оплата {amount} для {user_id} проведена и сохранена в БД")

async def handle_payment_request(user_id: int):
    try:
        # Если клиент закроет вкладку в браузере или отвалится по таймауту Nginx, 
        # веб-фреймворк (FastAPI/Aiohttp) вызовет task.cancel().
        # Shield проглотит сигнал отмены, и charge_credit_card гарантированно доработает до конца.
        await asyncio.shield(charge_credit_card(user_id, 100.0))
    except asyncio.CancelledError:
        print("Клиент разорвал TCP-соединение, но транзакция защищена от отмены")
        raise
```

## Основные методы Event Loop

|**Метод**|**Назначение**|
|---|---|
|**`asyncio.create_task()`**|Ставит корутину в очередь Event Loop для фонового выполнения. Возвращает объект `Task`. Обязательно сохраняйте ссылку на него, иначе сборщик мусора уничтожит задачу до завершения.|
|**`asyncio.wait_for(aw, timeout)`**|Выполняет awaitable-объект с заданным таймаутом. Если время истекает, выбрасывает `TimeoutError` и отменяет (`cancel()`) вложенную задачу.|
|**`asyncio.wait()`**|Принимает набор задач и ждет их выполнения. В отличие от `gather`, позволяет гибко указать момент возврата (например, `return_when=asyncio.FIRST_COMPLETED`).|
|**`asyncio.TaskGroup()`**|Современный (Python 3.11+) контекстный менеджер для группировки задач. Реализует структурную конкурентность: если падает одна задача, отменяются все остальные.|
|**`asyncio.gather()`**|Устаревающий, но популярный метод запуска списка корутин. При ошибке в одной возвращает исключение, но оставляет остальные задачи крутиться в фоне (утечка ресурсов).|

## Задачи

### Задача 1. Скрытая блокировка (Synchronous code in async)

**Условие:** Почему этот код не даст выигрыша в скорости по сравнению с обычным синхронным выполнением?

```python
import asyncio
import time

async def process_data(id):
    time.sleep(1)
    return id

async def main():
    tasks = [asyncio.create_task(process_data(i)) for i in range(3)]
    await asyncio.gather(*tasks)
```

**Разбор:** `time.sleep()` — синхронная функция ОС. Она блокирует весь текущий поток. Event Loop останавливается и не может переключаться между задачами. Корутины выполнятся строго последовательно, программа будет работать 3 секунды. **Решение:** Заменить на `await asyncio.sleep(1)`. Для реального блокирующего кода (например, вычисления или синхронные библиотеки) использовать `await asyncio.to_thread(func)`.

### Задача 2. Поведение asyncio.wait_for и отмена задач

**Условие:** Что будет напечатано в консоль и запишется ли значение в базу?

```python
import asyncio

async def db_write():
    try:
        await asyncio.sleep(2)
        print("Written to DB")
    except asyncio.CancelledError:
        print("Write cancelled")
        raise

async def main():
    try:
        await asyncio.wait_for(db_write(), timeout=1)
    except TimeoutError:
        print("Timeout")
```

**Разбор:** `wait_for` при истечении таймаута не просто прекращает ожидание, он внедряет исключение `CancelledError` внутрь выполняемой корутины. Функция `db_write` проснется от исключения на строке со `sleep`, выполнит блок except и не дойдет до записи. **Вывод:** "Write cancelled", затем "Timeout". **Интервью-подсказка:** Ожидается, что вы упомянете `asyncio.shield(db_write())`, если запись в БД критична и должна быть завершена даже при таймауте ответа клиенту.

### Задача 3. Состояние гонки (Data Race) в кооперативной многозадачности

**Условие:** Возможна ли здесь потеря обновлений счетчика, учитывая, что код работает в одном потоке?

```python
import asyncio

counter = 0

async def increment():
    global counter
    temp = counter
    await asyncio.sleep(0)  # Имитация I/O или переключения контекста
    counter = temp + 1
```

**Разбор:** Да, потеря данных гарантирована. Однопоточность спасает только между точками `await`. Когда первая корутина доходит до `await asyncio.sleep(0)`, она отдает управление. Вторая корутина читает то же самое значение `counter`, отдает управление. Затем обе записывают одно и то же инкрементированное значение. **Решение:** Использование `asyncio.Lock()`.

### Задача 4. Утечка при использовании gather

**Условие:** Что произойдет с задачей `long_task`, если `failing_task` упадет с ошибкой?

```python
import asyncio

async def failing_task():
    raise ValueError("Error")

async def long_task():
    await asyncio.sleep(10)
    print("Long task done")

async def main():
    try:
        await asyncio.gather(failing_task(), long_task())
    except ValueError:
        print("Caught error")
```

**Разбор:** `gather` не отменяет соседние задачи при ошибке в одной из них. `long_task` останется висеть в Event Loop как осиротевшая корутина ("orphan task"), потребляя память или удерживая сетевое соединение. **Решение:** Использовать `asyncio.TaskGroup()` (рекомендуется) или вручную ловить исключения через параметр `return_exceptions=True` в `gather`.
