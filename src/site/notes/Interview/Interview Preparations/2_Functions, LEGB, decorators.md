# Области видимости и правило LEGB

Порядок разрешения имен в Python строго регламентирован правилом LEGB: Local (Локальная), Enclosing (Объемлющая), Global (Глобальная модуля), Built-in (Встроенные объекты языка).

При компиляции исходного кода в байткод интерпретатор статически определяет область видимости каждой переменной. Если внутри функции есть операция присваивания переменной (например, `x = 1`), компилятор помечает `x` как локальную для всей этой функции. Для доступа к локальным переменным используются оптимизированные инструкции байткода `LOAD_FAST` и `STORE_FAST`, работающие через индексы массива, что значительно быстрее, чем поиск по хеш-таблице (словарю), который используется для глобальных переменных (`LOAD_GLOBAL`).

**Edge Cases / Trade-offs:** Ключевые слова `global` и `nonlocal` меняют статическое определение области видимости. `nonlocal` позволяет изменять переменную из ближайшей объемлющей области (Enclosing), но не глобальной. Использование этих инструкций создает побочные эффекты (side effects) и усложняет тестирование кода.

```python
x = 10

def outer():
    x = 20
    
    def inner():
        nonlocal x
        x = 30  # Изменит x внутри outer, глобальный x останется 10
        
    inner()
    print(x)  # Выведет 30
```

# Замыкания (Closures) и Cell-объекты

Замыкание — это вложенная функция, которая захватывает и запоминает состояние своей объемлющей области видимости, даже когда внешняя функция завершила выполнение и ее локальный контекст был уничтожен.

Под капотом это реализовано через атрибут `__closure__` объекта функции. Он содержит кортеж `cell`-объектов. `cell`-объект обеспечивает дополнительный уровень косвенности: он хранит ссылку на реальный объект в памяти. Это позволяет нескольким функциям (или функции и `nonlocal` переменной) ссылаться на одну и ту же ячейку и изменять ее состояние.

**Edge Cases / Trade-offs:** Замыкания продлевают жизненный цикл объектов. Если в объемлющей функции создается большой датафрейм, а вложенная функция его захватывает, этот датафрейм не будет уничтожен сборщиком мусора до тех пор, пока жива сама вложенная функция (утечка памяти через замыкание).

```python
def make_multiplier(factor):
    def multiplier(n):
        return n * factor
    return multiplier

mul_5 = make_multiplier(5)
# Изучаем внутренности замыкания
print(mul_5.__closure__)  # (<cell at 0x..., int object at 0x...>,)
print(mul_5.__closure__[0].cell_contents)  # 5
```

# Декораторы и functools.wraps

Декоратор — это функция (или объект), которая принимает другую функцию (или класс), расширяет ее поведение и возвращает заменяющий объект. Декораторы применяются на этапе парсинга модуля, а не в момент вызова функции.

При оборачивании функции оригинальный объект подменяется функцией-оберткой (`wrapper`). Из-за этого теряются метаданные оригинала: имя (`__name__`), строка документации (`__doc__`) и аннотации типов (`__annotations__`). Для решения этой проблемы обязательно применяется `@functools.wraps`.

Параметризованный декоратор (декоратор с аргументами) требует создания дополнительного уровня вложенности — фабрики декораторов.

```python
import functools
import time

def retry(retries=3):
    """Фабрика декораторов"""
    def decorator(func):
        @functools.wraps(func)
        def wrapper(*args, **kwargs):
            for attempt in range(1, retries + 1):
                try:
                    return func(*args, **kwargs)
                except Exception as e:
                    if attempt == retries:
                        raise
                    time.sleep(1)
        return wrapper
    return decorator

@retry(retries=5)
def fetch_data():
    pass
```

# Задачи с собеседований

### Задача 1. Late Binding (Позднее связывание) в замыканиях

**Условие:** Что выведет следующий код и почему? Как заставить его вывести ожидаемые `0, 1, 2`?

```python
def create_multipliers():
    return [lambda x: i * x for i in range(3)]

for multiplier in create_multipliers():
    print(multiplier(2))
```

**Разбор механики:** Код выведет `4, 4, 4`. Проблема заключается в позднем связывании переменных. Лямбда-функции внутри списка (list comprehension) захватывают **ссылку** на переменную `i` из объемлющей области видимости, а не ее текущее значение в момент итерации. Когда цикл `for` внутри `create_multipliers` завершается, переменная `i` остается в памяти со значением `2`.

Когда лямбда-функции вызываются позже, они обращаются к одному и тому же `cell`-объекту переменной `i` и видят там значение `2`. Следовательно, каждая функция вычисляет `2 * 2`.

**Решение:** Использовать значение по умолчанию для аргумента функции. Значения по умолчанию вычисляются статически во время компиляции функции, что позволяет захватить значение `i` на каждой итерации.

```python
def create_multipliers_fixed():
    # i=i фиксирует текущее значение на этапе создания лямбды
    return [lambda x, i=i: i * x for i in range(3)]
```

**Interview Tip:** Интервьюер проверяет понимание разницы между ссылкой на переменную и значением объекта. Если вы скажете, что лямбда "копирует переменную при создании" — это красный флаг. Нужно явно произнести термин "позднее связывание" (late binding) и упомянуть, что все функции смотрят на одну и ту же область памяти.

### Задача 2. UnboundLocalError и теневое копирование

**Условие:** Опишите поведение функции и объясните причину.

```python
a = 10

def process_data():
    print(a)
    a = 20

process_data()
```

**Разбор механики:** Код завершится с ошибкой `UnboundLocalError: local variable 'a' referenced before assignment`. Функция не выведет `10`. Как упоминалось в разборе LEGB, интерпретатор анализирует код на этапе компиляции. Он видит операцию присваивания `a = 20` и помечает имя `a` как локальную переменную для **всего** тела функции `process_data`.

Во время выполнения `print(a)` пытается прочитать локальную переменную `a`, но ей еще не было присвоено значение. Глобальная переменная `a` в этом контексте полностью игнорируется (shadowing).

**Решение:** Если цель — прочитать и затем изменить глобальную переменную, необходимо явно использовать директиву `global a` перед `print`. Если цель — использовать локальную, её нужно объявить до первого чтения.

### Задача 3. Декоратор Retry с экспоненциальной задержкой (Exponential Backoff)

**Условие:** Написать декоратор для асинхронных функций, который делает N попыток выполнения при возникновении исключения. Интервал между попытками должен увеличиваться экспоненциально.

```python
import asyncio
from functools import wraps
from typing import Callable, Any, Coroutine

def retry(retries: int, base_delay: float = 0.1) -> Callable:
    def decorator(func: Callable[..., Coroutine[Any, Any, Any]]) -> Callable:
        @wraps(func)
        async def wrapper(*args: Any, **kwargs: Any) -> Any:
            last_exc: Exception | None = None
            for i in range(retries):
                try:
                    return await func(*args, **kwargs)
                except Exception as e:
                    last_exc = e
                    # Экспоненциальное увеличение задержки: 0.1, 0.2, 0.4, 0.8...
                    await asyncio.sleep(base_delay * (2 ** i))
            raise last_exc or Exception("Unknown error")
        return wrapper
    return decorator
```

**Разбор механики:** Декоратор использует паттерн фабрики для передачи аргументов `retries` и `base_delay`. Обертка `wrapper` объявляется как `async def`, что позволяет использовать `await asyncio.sleep()`. Это критически важно: использование синхронного `time.sleep()` заблокировало бы весь Event Loop, остановив выполнение всех остальных корутин. Исключение сохраняется в `last_exc` и пробрасывается наружу только если цикл исчерпал все попытки.

**Edge Cases / Trade-offs:**

1. **Проблема грозящего стада (Thundering Herd):** Если микросервис падает и тысячи клиентов одновременно начинают ретраить запросы по одинаковому таймингу, они синхронно создадут пиковую нагрузку (DDoS) на сервер при его поднятии. Решение — добавление **Jitter** (случайного шума) к задержке: `await asyncio.sleep(base_delay * (2 ** i) + random.uniform(0, 0.1))`.
    
2. **Типы исключений:** Перехват базового `Exception` (как в примере) — это антипаттерн. Декоратор должен принимать кортеж `exceptions_to_check`, чтобы не ретраить фатальные ошибки (например, `SyntaxError` или `ValidationError`), а повторять только сетевые таймауты (`TimeoutError`, `ConnectionError`).
    
3. **Ограничение максимума:** В реальных системах необходимо вводить `max_delay`, чтобы экспонента не привела к ожиданию в несколько часов.
